# Amo Draft

在起草前先分类上下文，以编写目标聚焦的内容。

## 共享输出标记

首行内联前缀使用 `📝 [amo-draft]`。不要把该标记单独放在一个段落里。

## 使用场景

- 用户要求编写或编辑页面文案、网站内容、需求文档、实施说明、版本说明、发布说明或临时开发文档。
- 用户提供了参考项目、示例文本、风格来源、历史对话或可能与目标内容混淆的实施历史。
- 用户想要干净的最终产物，而不是对话或实施过程记录。

## 不使用场景

- 编码前方案设计；使用 `amo-feature`、`amo-improve`、`amo-fix` 或 `amo-refactor`。
- 方案二次压力测试；使用 `amo-best`。
- 已实现代码的风格审查；使用 `amo-review`。
- 基于真实实现生成面向用户的文档；使用 `doc-feat-desc`。
- 提交信息；使用 `git-smart-commit`。

## 上下文分流

写作前先分类可用上下文：

- **目标上下文**：属于最终产物的事实、需求、受众、产品身份、功能边界、已接受决策和约束。
- **参考上下文**：要模仿但不复制主题内容的风格、语气、结构、格式、布局模式或写作惯例。
- **过程上下文**：实施历史、调试说明、临时取舍、对话痕迹、被拒绝的想法和 agent 工作流细节。
- **排除上下文**：无关细节、偶然示例、不属于目标的参考项目事实，以及没有依据的模型假设。

把目标上下文作为内容使用。参考上下文只作为形式使用。除非用户明确要求包含，否则排除过程上下文和排除上下文。

## 关键规则

- 让目标产物始终围绕用户的目标主题。
- 不要让参考项目事实变成目标产品事实。
- 除非被要求，否则不要提到对话、agent、实施困难、调试路径、被拒绝的选项或写作过程。
- 除非用户要求，否则不要添加备注、风险、限制、实施问题或注意事项部分。
- 不要编造产品声明、业务事实、日期、指标、范围或约束。
- 如果缺少必要目标上下文，简短询问或使用明确占位符编写。
- 如果编辑既有文件，保持其预期结构，并移除偏离目标的内容。
- 只有当用户明确提供路径并要求写入、更新或替换时，才写入文件。

## 工作流

1. 识别目标产物和目标受众。
2. 将上下文分类为目标、参考、过程和排除上下文。
3. 判断缺失的目标上下文是否阻碍干净起草。
4. 按请求的格式和风格编写产物。
5. 最终输出前移除偏离目标的内容。
6. 只有在明确要求时才写入磁盘。

## 输出

输出标签和内容使用用户的语言。

对于简单起草，只输出最终产物：

```text
📝 [amo-draft] <标题或第一个标题>
...
```

对于复杂或被污染的上下文，先包含简短分流摘要：

```text
📝 [amo-draft] 场景：目标驱动内容草稿
上下文分拣：
- 已纳入：
- 仅作参考：
- 已排除：
正文：
```
