# amo-improve

## 元数据

- name: `amo-improve`
- description: 当用户在编码前询问如何改进、扩展、调整或重新设计既有功能或行为时使用。不要用于全新功能、损坏行为、纯重构或方案二次挑战。
- version: `0.2.0`

# Amo Improve

规划对既有功能的有意变更，不让旧实现细节决定目标设计。

## 共享输出标记

首行内联前缀使用 `🧰 [amo-improve]`。不要把该标记单独放在一个段落里。

## 使用场景

- 当前行为已经存在，但期望行为不同。
- 用户希望改进、扩展、调整或重新设计已有功能。
- 工作可能涉及兼容、迁移、交互变化或修改既有模块。

## 不使用场景

- 行为完全是新的；使用 `amo-feature`。
- 已有行为错误、损坏或异常；使用 `amo-fix`。
- 主要问题是结构且没有行为变化；使用 `amo-refactor`。
- 已有候选方案需要压测；使用 `amo-best`。

## 最佳标准

推荐方案前选择并说明一个标准：

- **目标态最佳**：开发阶段且没有明确约束时的默认值；优先正确边界、长期可维护性、必要重构，并且不围绕遗留实现扭曲设计。
- **约束内最佳**：当用户要求快速交付、兼容性、最小改动、短期交付或有限范围时使用。
- **演进式最佳**：当目标设计正确，但应该以安全的分阶段方式交付时使用。
- **风险最低最佳**：当生产、数据、安全、认证/权限、支付、迁移或回滚风险占主导时使用。

## 工作流

1. 识别当前行为和目标行为。
2. 选择最佳标准并解释原因。
3. 检查实现、ownership 边界，以及涉及 UI 时的渲染行为。
4. 判断是适配既有代码、重塑代码，还是分阶段交付目标设计。
5. 推荐一个方案，并说明取舍、影响范围和验证方式。

## 核心规则

- 目标行为优先于偶然形成的旧实现。
- 除非所选最佳标准要求，否则不增加兼容工作。
- 没有代码库证据或明确用户需求时，不要添加猜测性兼容路径、fallback 分支或遗留处理。
- 无关清理不纳入范围。
- 如果实施过程中发现更好的方式，切换前先暂停并解释。
