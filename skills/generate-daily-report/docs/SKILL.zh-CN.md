# Generate Daily Report

将零散工作记录整理成简洁、真实的日报，说明发生了什么、还剩什么以及下一步做什么。

## 使用场景

- 用户提供已完成任务和明日计划，需要一份可直接提交的日报。
- 日报表单、截图、历史日报或评审反馈规定了结构或质量标准。
- 简短任务名称需要补充更清楚的结果、进展、业务价值、不足或验收标准。
- 需要借助项目术语改善表达，但不能编造项目事实。

## 不使用场景

- 除非用户明确要求沿用日报结构，否则不要用于周报、月报、绩效总结或项目复盘。
- 用户要求只根据输入生成时，不要检查仓库。
- 不要把仓库改动当成用户完成、测试、发布或负责该工作的证明。

## 读取质量规则

起草前读取 [references/report-quality.md](../references/report-quality.md)。使用其中的栏目要求、转换规则和最终检查清单。示例只用于参考结构。

## 根据反馈校准

如果存在历史日报、评分或评审反馈，起草前应用质量参考文件中的反馈校准规则。

## 选择上下文模式

根据用户表达和可用上下文选择一种模式：

1. **仅输入模式**：用户明确要求、没有可用项目，或日报包含多个无关项目时，只使用用户记录和提供的材料。
2. **项目增强模式**：任务包含项目特有术语且存在相关工作区时默认使用。只读取理解术语和价值所需的上下文。
3. **严格核对模式**：仅当用户明确要求核对当前项目改动时使用。单独报告不一致，不要静默替换用户声明的事实。

项目增强模式按以下顺序读取：

1. 如果存在，读取 `.codex/daily-report-context.md`。
2. 读取适用的 `AGENTS.md`、README 和相关项目文档。
3. 仅在需要解释术语或核对用户明确要求验证的声明时，检查相关代码或只读 Git 证据。

`.codex/daily-report-context.md` 是可选文件。不存在时正常继续。不要要求每项任务都属于当前仓库，也不要把无关仓库事实写入日报。

## 信息来源优先级

按以下顺序使用信息：

1. 用户明确提供的完成状态、结果、阻塞和计划。
2. 用户提供的表单、截图、历史日报和评审反馈。
3. 可选项目上下文和相关项目文档。
4. 只读仓库证据。
5. 仅用于谨慎、非量化价值概括的通用领域知识。

发生冲突时，以用户明确表达为准；仅在严格核对模式下，将重要的证据差异写在日报正文之外。

在内部将计划写入的句子分为：

- **明确事实**：用户或源材料明确提供。
- **有依据的解释**：任务描述或项目上下文支持的谨慎能力、价值说明。
- **无依据的声明**：缺少来源的测试、发布、指标、范围、归属或结果，必须排除。

## 工作流程

1. 确认日报语言、目标表单、必填栏目和详细程度。
2. 如果提供了历史评分或反馈，先据此校准质量要求。
3. 提取已完成工作、范围、进展、验证、不足、阻塞、明日工作和经验。
4. 选择上下文模式，只收集最低限度的相关信息。
5. 按照质量参考文件中的栏目要求和安全转换规则编写所有必填栏目。
6. 执行其中的最终检查清单，输出可以直接粘贴到目标表单的内容。

## 关键规则

- 将前述信息来源优先级和句子分类作为每条日报内容的强制准入规则。
- 严格遵守所选上下文模式，并将严格核对发现的不一致保留在日报正文之外。
- 完整执行质量参考文件中的事实、栏目和检查清单要求，不得弱化。
- 只有缺失信息会实质性改变日报时才简短提问，否则使用保守表达直接生成。

## 输出

用户提供表单时，严格遵循其结构；否则默认使用用户语言输出以下栏目：

```text
今日工作总结
哪些事情没有做好
哪些事情解决不了
明日计划
今日思考
```

用户要求精简且没有提供必填表单时，只返回其需要的栏目，通常是今日总结和明日计划。不得省略表单要求的栏目。除非用户要求，否则不要在日报中加入信息来源分析、置信度标签或起草说明。
