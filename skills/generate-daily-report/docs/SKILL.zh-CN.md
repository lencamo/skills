# Generate Daily Report

将当天真实工作整理成简洁、可直接粘贴到日报表单中的内容。

## 使用场景

- 用户提供已完成工作、未完成工作、阻塞、思考或明日计划。
- 用户要求根据今天的提交、代码改动或开发记录生成日报。
- 当前存在相关仓库，用户要求生成日报但没有提供完整任务清单；默认以当前用户当天的提交和工作区改动作为任务输入。
- 截图、历史日报、评分或评审反馈规定了表单和写作风格。

## 不使用场景

- 除非用户明确要求沿用日报结构，否则不要用于周报、月报、绩效总结或复盘。
- 用户明确要求只根据输入起草时，不要检查仓库。
- 不要仅因为代码存在就声称已经测试、部署、验收、取得指标或产生线上结果。

## 读取质量规则

起草前完整读取 [references/report-quality.md](../references/report-quality.md)。其中定义了仓库证据处理、面向受众的术语转换、栏目要求、历史风格校准、自然兜底表达和最终检查清单。

## 选择信息来源模式

根据请求和可用上下文选择一种主要模式：

1. **仅输入模式**：用户明确要求、没有相关仓库，或日报横跨多个无关项目时，只使用用户记录和提供的材料。
2. **仓库驱动模式**：用户提到 Git、提交、代码改动、工作区，或在相关仓库中要求生成今日日报但没有给出完整任务清单时使用。
3. **严格核对模式**：仅当用户明确要求根据仓库核对其工作声明时启用。重要差异应放在日报正文之外。

仓库驱动模式下：

- 当前 Git 用户当天提交的实现，默认视为已完成的开发工作；但提交文字或差异明确表示调研、实验或部分进展时，应保留真实状态。
- 暂存、未暂存及相关未跟踪改动也属于今日工作，但要按真实状态表达；未提交工作通常写为“推进中”或“完善中”，不能自动写成已完成。
- 用户明确补充的其他任务即使不在仓库中，也要加入日报。
- 按工作成果合并相关提交和文件，不要按提交或文件逐条罗列。

仅在解释项目术语或影响时读取 `.codex/daily-report-context.md`、适用的 `AGENTS.md`、README 和相关项目文档，不要把整个项目待办写成今日工作。

## 证据与正文边界

证据只用于内部判断，日报正文应像本人正常汇报工作。除非用户要求审计过程：

- 正文中不得出现“根据 Git 提交”“提交记录显示”“工作区中”“现有信息未体现”“无法从记录确认”等表达。
- 不要把缺少证据写成不足、阻塞或免责声明。尤其不能因为没有看到测试记录，就认定测试未完成。
- 不要输出提交哈希、文件数量、增删行统计、置信度、信息来源分析或起草说明。
- 日报前不要解释生成方式，只返回可直接提交的正文。

用户明确说明的状态和计划优先于仓库判断。删除没有依据的测试、发布、指标、工时、归属和业务结果声明。

## 工作流程

1. 确认日报日期、语言、必填表单、目标受众和信息来源模式。除非用户或表单另有说明，默认读者是不了解仓库内部规划术语的领导或业务相关方。
2. 如果提供了历史日报或评分，提取稳定的标题、内容密度、兜底用语和反复出现的质量反馈。
3. 只收集今日任务需要的最低限度证据。仓库驱动模式下检查当天提交和当前工作区改动，再按需读取目标差异以理解工作成果。
4. 将相关实现细节合并成相互独立的任务结果，按目标受众转换内部规划和实现术语，并保留真实完成状态。
5. 起草所有必填栏目。没有明确不足或阻塞时使用自然兜底表达，不要解释信息为何缺失。
6. 根据用户计划、当前未完成工作和直接相关的后续验证，保守整理明日计划，不得扩展出新的功能待办。
7. 结合当天工作写一条具体思考，并执行质量检查清单。

## 输出

用户提供表单时严格遵循其结构；否则中文日报默认使用以下标题：

```text
📌 今日工作总结
⚠️ 哪些事情没有做好
❓ 哪些事情解决不了
📅 明日计划
💡 今日思考
```

多项相互独立的工作总结使用编号。明日计划中的多个动作如果服务于同一目标，或构成“讨论、明确、实施”等连续步骤，应合并为一个紧凑段落；只有计划相互独立，或表单、历史风格明确偏好编号时才分点。单项内容或无问题说明使用简短段落。除非用户明确要求，否则不要添加“AI 改进建议”栏目。

如果用户明确只需要部分栏目，则只返回对应内容；其他情况下保留默认五个栏目，确保结果可直接提交。
