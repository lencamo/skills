# amo-refactor

## 元数据

- name: `amo-refactor`
- description: 当用户在编码前询问如何重构、拆分模块、澄清架构、移动 ownership、降低耦合，或修复不清晰的状态、数据流或组件边界时使用。不要用于普通功能工作、bug 修复或方案二次挑战。
- version: `0.2.0`

# Amo Refactor

当边界、ownership 或耦合是主要问题时，规划结构性变更。

## 共享输出标记

首行内联前缀使用 `🧱 [amo-refactor]`。不要把该标记单独放在一个段落里。

## 使用场景

- 用户问是否应该重构，或如何重构。
- 模块边界、组件边界、状态归属、数据流或架构不清晰。
- 复杂度或耦合让下一步修改变得高风险或难推理。

## 不使用场景

- 主要目标是新增行为；使用 `amo-feature`。
- 主要目标是改变已有行为；使用 `amo-improve`。
- 主要目标是修复损坏行为；使用 `amo-fix`。
- 已有重构方案需要压测；使用 `amo-best`。

## 最佳标准

推荐重构前选择并说明一个标准：

- **目标态最佳**：开发阶段且没有明确约束时的默认值；优先正确边界、长期可维护性、必要重构，并且不围绕遗留实现扭曲设计。
- **约束内最佳**：当用户要求快速交付、兼容性、最小改动、短期交付或有限范围时使用。
- **演进式最佳**：当目标边界正确，但应该以安全的分阶段方式交付时使用。
- **风险最低最佳**：当生产、数据、安全、认证/权限、支付、迁移或回滚风险占主导时使用。

## 工作流

1. 识别结构压力：ownership、耦合、体积、重复或不清晰的流程。
2. 选择最佳标准并解释原因。
3. 检查当前边界、依赖和行为保持约束。
4. 定义目标边界和职责。
5. 推荐一个有范围控制的重构方案，并说明取舍和验证方式。

## 核心规则

- 只有结构本身是问题时才重构，不因为代码“不够完美”而重构。
- 先确定职责边界，再谈改法。
- 除非用户明确要求，否则保持行为不变。
- 没有代码库证据或明确用户需求时，不要添加猜测性兼容路径、fallback 分支或遗留处理。
- 如果实施过程中发现更好的方式，切换前先暂停并解释。

## 输出

```text

最佳标准：

目标边界：

取舍：
影响范围：

```
