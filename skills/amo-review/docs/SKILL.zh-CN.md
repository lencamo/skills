# Amo Review

审查已实现代码的风格、冗余、无必要抽象和 TypeScript 类型清晰度。

## 共享输出标记

首行内联前缀使用 `🧹 [amo-review]`。不要把该标记单独放在一个段落里。

## 使用场景

- 用户要求代码风格审查、冗余审查或清理建议。
- 代码已经实现，或有 diff/文件可供审查。
- 审查应该聚焦无必要抽象、TypeScript 类型噪音、composable 使用清晰度或可维护性问题。

## 不使用场景

- 还没有实现；使用 `amo-feature`、`amo-improve`、`amo-fix` 或 `amo-refactor`。
- 方案需要最佳方案压力测试；使用 `amo-best`。
- 用户要求 bug 根因分析；使用 `amo-fix`。
- 用户要求生成提交信息。

## 工作流

1. 判断前先检查真实代码或 diff。
2. 只识别对维护性、可读性、类型安全或行为来源有具体影响的问题。
3. 相比宽泛的风格意见，优先给出更少、更高置信度的问题。
4. 区分必须修复的问题和可选清理。
5. 可用时提供精确文件/行引用。

## 代码风格规则

- 不要为单一调用点或单行逻辑创建或保留 helper、wrapper、adapter、parser、type guard 或类似中间抽象。移动代码、提升作用域、导出 API 或重构后，按调用点重新检查。除非抽象明显提升错误边界、可测试性或可读性，否则内联表达式。
- 使用 composable 返回值时，展示用的 ref/computed 变量可以按需解构。会触发状态变更或副作用的函数默认保留 composable 命名空间调用，以保持行为来源清晰。

## TypeScript 类型规则

- 优先使用 TypeScript 推断。避免为中间变量、内部函数和简单返回值添加冗余类型注解。
- 公共边界显式声明类型：DTO、组件 props、导出函数入参、公共协议、请求 payload 和响应 data 结构。
- 不重复表达已经由泛型或框架 wrapper 确定的类型。例如，业务 API、controller 和 store 不应手写 `Promise<ApiResponse<T>>` 或 `Promise<ApiResult<T>>`。
- 不手写第三方库或工厂函数已经能可靠推断的复杂泛型返回类型。需要复用时，优先使用 `ReturnType<typeof fn>` 等简单工具类型。
- 类型设计保持简单。优先使用直接的 `interface` / `type`；避免为少量代码引入复杂泛型、条件类型、映射类型或过度抽象的类型模型。
- 不要仅为了语义化命名、未来扩展或通用化，在没有当前收益时添加别名、包装函数、动态 key parser 或中间抽象。自己维护且结构清晰的代码，优先直接访问和直接调用，让类型和值的来源保持单一且可追踪。
- TypeScript 收窄优先使用直接表达式和已有数据结构。不要添加只被一个调用点使用的 type guard。只有当判断逻辑复杂、被多处复用或属于公共边界 API 时，才提取 type guard。
- 按需提取共享类型。只有当多个 app 或 package 稳定复用同一组类型时，才新增共享类型包。

## 关键规则

- 除非抽象是单次使用、冗余、误导或隐藏行为来源，否则不要要求移除抽象。
- 当 TypeScript 推断已经清晰且局部时，不要要求显式类型。
- 不要把风格偏好改写成问题，除非它们提升可维护性或正确性。
- 不要从风格审查提出大型重构；如果问题属于架构问题，说明它应归入 `amo-refactor`。
