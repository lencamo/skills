# Solution Design Review

当用户要求计划、诊断、实施方式、最佳方案、根因分析、重构策略或取舍讨论时，在提出或实施方案前使用此 skill。

## 使用场景

- 用户询问“你会如何实现这个？”。
- 用户要求最佳方案，而不仅仅是最小补丁。
- 用户询问 bug 为什么发生以及如何修复。
- 用户想比较实现选项。
- 任务涉及 UI 一致性、交互状态、组件边界、架构或重构。
- 快速局部补丁可能有效，但可能隐藏更深的 ownership 或设计问题。

## 不使用场景

- 当用户明确要求直接做小修改且不需要讨论时。
- 纯机械文件修改，没有设计决策。
- 提交信息生成。
- 面向用户的文档写作。

## 工作流

1. **问题分类**
   - Bug 修复
   - 功能实现
   - 重构
   - UI/设计一致性
   - 交互或状态 ownership
   - 架构或模块边界
   - 平台或运行时行为

2. **先检查相关上下文**
   - 提出方案前先读取相关代码、配置或既有模式。
   - 区分现象和根因。
   - 当渲染输出、事件流或 ownership 边界重要时，不要只根据 class name 或表面行为推断。

3. **区分快速修复和耐久方案**
   - 如果存在快速修复，标记它是快速修复。
   - 如果存在更好的长期方案，解释为什么它更好。
   - 不要把 workaround 表述为最佳方案。

4. **推荐一个方案**
   - 清晰说明推荐方案。
   - 解释取舍和影响范围。
   - 避免对小变更过度设计，但当用户要求最佳方案时，不要默认最小改动。

5. **说明实施影响**
   - 可能受影响的文件或模块
   - 行为变化
   - 兼容性或迁移关注点
   - 验证计划

6. **批准后，实施推荐方案**
   - 不要静默降级为更快补丁。
   - 如果实施中发现更好的方式，切换策略前先暂停并解释。

## 关键规则

- 先根因，后修复。
- 先 ownership 边界，后 patch。
- 先渲染行为，后 class-name 假设。
- 先取舍，后推荐。
- 最佳方案意味着耐久、可维护、适合项目，不一定是最大重构。
- 当用户在开发阶段明确要求最佳方案时，即使需要重构，也要优化目标设计；除非用户要求兼容，否则不要让方案偏向与既有代码向后兼容。
