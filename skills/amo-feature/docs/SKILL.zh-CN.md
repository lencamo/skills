# amo-feature

## 元数据

- name: `amo-feature`
- description: 当用户在编码前询问如何设计或实现新功能、新能力、新工作流、新页面、新 API 或新行为时使用。不要用于 bug 修复、对既有行为的有意变更、纯重构或方案二次挑战。
- version: `0.2.0`

# Amo Feature

在实施前设计新功能。

## 共享输出标记

首行内联前缀使用 `🧩 [amo-feature]`。不要把该标记单独放在一个段落里。

## 使用场景

- 请求的行为当前不存在。
- 用户询问如何实现一个新功能或新需求。
- 工作需要需求边界、技术形态、受影响模块、取舍和验证。

## 不使用场景

- 既有行为正在被改变或扩展；使用 `amo-improve`。
- 既有行为损坏；使用 `amo-fix`。
- 结构是主要问题且没有新行为；使用 `amo-refactor`。
- 已经存在候选方案并需要挑战；使用 `amo-best`。

## 最佳标准

推荐方案前选择并说明一个标准：

- 目标态最佳：开发阶段默认值，优先正确边界、长期维护和必要重构。
- 约束内最佳：用户明确要求快速、兼容、少改、短期交付或范围受限。
- 演进式最佳：目标设计正确，但需要分阶段安全交付。
- 风险最低最佳：生产、数据、安全、权限、支付、迁移或回滚风险主导。

## 工作流

1. 明确目标行为和成功标准。
2. 选择最佳标准并解释原因。
3. 检查相关代码、模式和约束。
4. 推荐一个设计，并明确取舍。
5. 说明受影响模块、行为变化、风险和验证方式。

## 关键规则

- 除非需求要求，否则不要把一个功能做成平台。
- 优先简单、可维护、生产可用的设计。
- 没有代码库证据或明确用户需求时，不要添加猜测性兼容路径、fallback 分支或遗留处理。
- 如果必须改变既有行为，指出其中的 `amo-improve` 部分。
- 如果实施过程中发现更好的方式，切换前先暂停并解释。
