# amo-fix

## 元数据

- name: `amo-fix`
- description: 当用户询问既有行为为什么损坏、错误、不稳定、回归、异常，或运行时/构建行为失败，并希望在编码前获得 bug 修复方案时使用。不要用于计划内功能变更、纯重构或方案二次挑战。
- version: `0.2.0`

# Amo Fix

从现象到根因诊断 bug，然后再选择修复方式。

## 共享输出标记

首行内联前缀使用 `🛠️ [amo-fix]`。不要把该标记单独放在一个段落里。

## 使用场景

- 既有行为错误、损坏、不稳定、回归、不一致或异常。
- 运行时、构建、框架、状态、数据流或渲染行为不符合预期。
- 快速补丁可能隐藏更深的 ownership、状态或流程问题。

## 不使用场景

- 请求的变更是有意的产品行为；使用 `amo-improve`。
- 任务是新能力；使用 `amo-feature`。
- 结构是主要问题且没有 bug 现象；使用 `amo-refactor`。
- 已提出的修复需要挑战；使用 `amo-best`。

## 最佳标准

推荐修复前选择并说明一个标准：

- **目标态最佳**：开发阶段且没有明确约束时的默认值；优先正确边界、长期可维护性、必要重构，并且不围绕遗留实现扭曲设计。
- **约束内最佳**：当用户要求快速交付、兼容性、最小改动、短期交付或有限范围时使用。
- **演进式最佳**：当根因修复需要目标设计工作，但应该以安全的分阶段方式交付时使用。
- **风险最低最佳**：当生产、数据、安全、认证/权限、支付、迁移或回滚风险占主导时使用。

## 工作流

1. 说明现象和期望行为。
2. 选择最佳标准并解释原因。
3. 检查真实代码路径、状态/数据流、运行时行为或渲染输出。
4. 区分根因、现象和次生影响。
5. 推荐一个修复方案，并说明取舍、回归风险和验证方式。

## 关键规则

- 先根因，后修复。
- 不要把 workaround 表述为最佳修复。
- 没有代码库证据或明确用户需求时，不要添加猜测性兼容路径、fallback 分支或遗留处理。
- 如果真正修复需要重构，明确说明。
- 如果实施过程中发现更好的方式，切换前先暂停并解释。
