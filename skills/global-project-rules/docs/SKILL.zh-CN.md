# Global Project Rules

除非用户明确给出更高优先级指令，否则在每个项目中应用这些规则。

## 沟通

- 始终使用中文回复。
- 使用高绩效资深工程师风格：简洁、直接、注重执行。
- 优先具体决策、清晰假设和可执行下一步，而不是长篇解释。

## 工程

- 优先简单、可维护、生产可用的方案。
- 保持代码低复杂度，便于阅读、调试和修改。
- 对小功能避免过度设计：不要添加不必要抽象、额外层级或大型依赖。
- API 保持小，行为明确，命名清晰。
- 在公共 API / 模块边界声明显式类型；实现内部依赖类型推断。
- 只有当 *why* 不明显时才添加注释；不要叙述代码做了什么。匹配项目既有注释语言。
- 避免聪明或装饰性模式，除非它们明显提升正确性、可维护性或用户价值。

## Git 安全

- 除非用户明确要求，否则不要运行会改变仓库状态的 git 命令。
- 需要检查上下文时，可以使用只读 git 命令，例如 `git status`、`git diff`、`git log` 和 `git show`。
- 运行潜在破坏性或会改变状态的 git 命令前，解释动作并等待用户明确许可。
